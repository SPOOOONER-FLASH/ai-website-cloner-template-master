### 9.2 对“是不是图片太大”的直接回答

**图片是主要字节量，但不是“某一张图片有几 MB”这种简单问题。** 当前所有图片都小于 400 KB，首张 LCP Hero 只有 119,540 B；然而移动端仍下载 1600–2400px 原图，轮播三张图同时进入首屏 DOM，浏览器还会提前抓取近首屏 lazy 图片。源站连接、吞吐和缓存失效进一步把这些 100–265 KB 的图片拖到数秒甚至十几秒。

| 已证实项 | 证据 | 判断 |
|---|---:|---|
| 全站 `public` 图片 | 1,402 个，43.25 MiB；最大 391,848 B | 总库存大不等于首屏全下载，不能用总目录大小判断打开速度 |
| 产品图片 | 1,342 个，37.74 MiB，平均约 28 KB | 不是首页冷加载主因，不建议先无差别重压全部产品图 |
| 首页完整滚动的唯一图片 | 15 个唯一 URL，其中 13 张位图约 2.64 MB | 总量可继续优化，但真正关键是首屏调度和设备尺寸 |
| 首批图片 | 不同冷样本约 0.85–1.67 MB，占首次传输约 77%–86% | 图片是首屏最大字节类别 |

| 首张 Hero | 2400×943、119,540 B；移动显示宽约 358–363px | 压缩体积不失控，但下载了远超需要的像素；4:3 移动容器还裁掉约一半横向内容 |

- `next.config.ts` 使用 `output: "export"` 与 `images.unoptimized: true`；

### 9.3 服务器、缓存与网络是同等重要的主因

多轮独立请求显示：

- gzip 首页 HTML 约 14,176 B，解压约 78,179 B；`curl` 五次 TTFB 中位约 0.80 秒；
- 119,540 B 首图五次 TTFB 中位约 1.05 秒，总时长中位约 2.86 秒；
- 浏览器冷会话的连接/TLS 约 1.44–1.46 秒，实验 LCP 约 3.9–5.0 秒；
- 生产响应只有 nginx，未见 `Age`、`Via`、`X-Cache` 等 CDN 命中证据；当前更像用户直连单一源站；
- HTML、WebP 和 RSC 没有明确 `Cache-Control`；内容哈希 CSS/JS 只有约 12 小时缓存，没有一年 `immutable`；
- 同一张内容、大小和 SHA-256 不变的 WebP，其 `Last-Modified`/ETag 在小样本中约每 5–10 秒变化一次；旧验证器随后会重新得到 200。

这高度说明服务器发布链路在无内容变化时仍反复覆盖或更新时间戳，导致条件缓存持续失效，并可能争抢磁盘 I/O。即使把首图再压小几十 KB，也无法消除 1–2 秒连接/首字节和缓存重验证成本。

### 9.4 另一个确定性问题：Next 静态预取 404

生产浏览器持续请求点号形式的静态 RSC 预取 URL，例如：

```text
/contact/__next.contact.__PAGE__.txt?_rsc=...
/products/lock-cases/__next.products.$d$category.__PAGE__.txt?_rsc=...
/products/panic-exit-devices/305-fire-door-panic-exit-device/__next.products.$d$category.$d$slug.__PAGE__.txt?_rsc=...
```

这些请求返回 404；而本地 `out/` 中存在的是目录形式，例如：

```text
out/contact/__next.contact/__PAGE__.txt
out/products/lock-cases/__next.products/$d$category/__PAGE__.txt
```

长时间静置样本在 18.5 分钟内累计 181 个 `__PAGE__.txt` 预取、约 1.15 MB，每个轮播周期又重复出现。直接请求也确认：目录形式 URL 返回 200，点号形式 URL 返回 404。它不一定决定首次 LCP，但会持续占用网络、电量和连接，是必须修的部署/Link 预取问题。

### 9.5 建议的修复顺序

1. **P0：停止无变化的 10 秒重拷贝。** 服务器同步改为只在新提交时增量更新并保留 mtime；先确认真实发布脚本/定时器，再改，避免误伤当前上线链路。
2. **P0：在源站前增加 CDN，并建立正确缓存层级。** HTML 短缓存；内容哈希 CSS/JS 一年 `public, max-age=31536000, immutable`；图片若使用内容哈希文件名也可永久缓存，否则先采用较短 `max-age` + `stale-while-revalidate`。
3. **P0：构建期生成响应式图片。** 保持静态站即可，用 Sharp 为首页/Company/Projects 大图生成 480/800/1200/1600/2400 候选，用 `<picture>`、`srcset`、`sizes` 选择；Hero 另做 4:3 移动构图。内存模型显示：移动首批六张位图约 1.094 MB 可降至约 165 KB，潜在节省约 85%；完整首页 13 张可从约 2.638 MB 降至约 416 KB，潜在节省约 84%。这是估算，最终需视觉 QA。
4. **P0：轮播首屏只挂 active slide。** 首图完成/LCP 后再 idle 预取 next，DOM 最多保留当前和下一张；可立即避免首次同时下载另外 375,052 B 的隐藏 Hero。
5. **P1：修复 RSC 预取路径，或临时关闭非关键 Link 的 `prefetch`。** 同时确认 nginx 对点号、`$` 和 `.txt` 的映射；禁止每个轮播周期重新预取同一失败 URL。
6. **P1：对下方图片采用可控 IntersectionObserver。** 保留现有 aspect-ratio 占位，距视口约 300–600px 才挂真实 `src`，而不是完全依赖浏览器不可控的 native lazy 阈值。
7. **P2：自托管 Archivo WOFF2，随后再考虑 Brotli。** Google Fonts 有明显冷请求波动；JS/CSS 已 gzip，字体优化有价值但优先级低于缓存、图片和 404。

### 9.6 动态数据库与登录的初步架构判断

全动态、数据库和登录体系都能实现，但当前公共站的商业目标是“品牌/产品展示 → 邮箱询盘或阿里巴巴成交”，没有证据支持立即把 471 个静态页面整体改成每次请求查数据库。

Codex 的初步推荐是 **路线 2：静态公共站 + 托管数据库/Auth/Storage + 发布触发构建**：

- 公共产品、案例和 SEO 页面继续静态化，保留当前 URL 与速度上限；
- 只有真正需要状态的功能进入数据库，例如询盘、客户/业务员账号、权限、CRM 状态、审计日志；
- 后台登录使用成熟 Auth，权限在服务端/API 校验，不能只靠前端隐藏按钮；
- 内容发布仍生成版本化静态结果，数据库故障不应让公共目录整体打不开；
- 先迁移一个垂直切片（例如询盘入库 + 员工登录 + 状态流转），验证权限、备份、邮件、审计与成本后，再决定是否扩大。

只有在业务明确要求实时库存、报价、客户订单、经销商私有价格或强一致审批时，才建议进入路线 3（Next.js Node/Docker + PostgreSQL）。路线 3 会新增运行时、数据库迁移、会话安全、备份恢复、告警和长期运维责任，不应只为了“后台看起来像截图”而重写整站。

### 9.7 建议的 Codex × Claude 最小协作协议

- 不使用全局锁；开工前读取 status、最近 commits、diff 与最新 agent update。
- 陌生未提交文件默认属于对方。非重叠文件可并行；同一已修改文件只有一个实现者，另一方只读复核。
- 一个提交只解决一个完成主题，并在同一提交附独立 update；精确暂存，禁止在脏树中无审查批量 add。
- `out/` 只由最后整合者在源代码稳定后执行一次完整构建并提交，避免双方交替生成数千个构建差异。
- Claude 建议主责既有产品数据、Decap CMS、迁移脚本与当前 Product Finder 上下文；Codex 建议主责视觉系统、响应式图片流水线、性能预算与独立发布核验。动态 Auth/DB 应由一方实现，另一方做权限/数据迁移/回滚复核。
- 性能改动至少留存移动/桌面冷加载基线：请求数、图片字节、总字节、TTFB、LCP、404 数；正式上线门槛待双方用同一工具和同一网络条件共同确定。
- `HANDOFF.md` 只保留当前事实与外部依赖；完成项必须附提交和验证，过时的“尚未做”应在同一 PR 更新。

### 9.8 仍需 Claude 与甲方确认

- 服务器上每 5–10 秒重复覆盖或更新时间戳的真实进程、配置和可回滚方式；
- 是否接受 CDN/对象存储，正式域名何时切换；
- 图片是否允许构建时生成内容哈希文件名，或必须保持当前稳定 URL。

甲方已经确认：如果未来启动登录，一期唯一用户是 HYDE / Cantonlock 内部员工，不开放经销商或
终端客户注册。当前静态品牌站已满足“门面 + 邮箱/阿里导流”目标，登录/数据库暂缓，等真实询盘
管理需求出现后再定义首个闭环和权限矩阵。

### 10.6 动态化边界

数据库与登录技术上都能做，但这轮没有把 471 个公共页面改成 SSR/查库，后续也不应为了“看起来
更像后台”而重写。甲方已确认网站首先是高格调品牌门面、详尽产品矩阵和邮箱/阿里导流工具，
SEO 与 GEO/AEO 是长期增长重点。

当前决策是：

1. 先接通 Categories / Downloads 的 CMS 单一内容源；
2. 继续用静态页面、Decap 与构建期索引支撑公开站，不增加运行时数据库依赖；
3. 登录/数据库暂缓；若真实询盘量需要后台，首期只做 HYDE / Cantonlock 内部员工的询盘入库、
   分配、状态、备注、邮件重试与审计，不开放注册；
4. 在任何 PII 入库前补正式隐私页、保留/删除规则、服务端校验、限流与 Turnstile；
5. 只有未来明确需要实时库存、订单或强审批，才重新论证全动态 Node/PostgreSQL。
