## 5. 两台电脑怎么协作（重要）

甲方带走 86132 那台，johns 这台也还在。**git 是两台之间唯一的通道。**

**唯一的禁忌**：仓库里提交了 21,000 多个构建产物（`out/` + `out-rayen/`）。
两台都改都构建都推的话，后推的会被 git 拒绝，然后 `git pull` 会**逐文件合并这两万个
产物**，合出来是两次构建的混合物 —— 一部分页面来自 A 那次，一部分来自 B。
**全程不报错**，因为每个文件单独看都没冲突。

**规矩**：只在一台上改和构建，另一台只 `git pull` 不改。
详见 `docs/collaboration/CLIENT-RUNBOOK.md` 第 7、8 节（写给甲方看的版本）。

## 6. 暂存的教训，别重犯

**不要用 `git add -A -- <目录>`。** 这个仓库是多个会话共享工作树的。
2026-09-09 我用 `git add -A -- content` 暂存，把另一个会话**正在写、还没写完**的
五个产品 JSON 按了快门，提交里是截断的、解析不了的内容。
是提交完看 `git status` 还剩 39 个改动、去查「为什么还没干净」才发现的。

**按明确路径暂存**：`git add -- path/a path/b`。
动别人的文件之前**先 `cp` 一份备份**（我修的时候 `git show HEAD~1:file > file` 在文件
不存在时报错退出，而 shell 重定向已经先把文件清成 0 字节，靠备份才救回来）。

## 7. 两个站并行时，图片流水线为什么不会再撞车（2026-09-10）

甲方问：「两个网站肯定要并行同时工作，不能受影响，你给个办法」。这是真撞过一次之后加的。

**撞的那次长什么样**：我在跑 `npm run assets:watermark`（全量重算 3000 张），
另一个会话同时在批量重命名产品图。sharp 抛 `Input file is missing` 整个跑崩 ——
而上一轮的 manifest 还留在磁盘上看起来一切正常，后面 2000 多张保持旧内容。
**坏在崩得看不出来**，不是坏在崩。

**改法两条，两个脚本都做了**：

1. **增量**：记住每张源图的 SHA 和上次的判定。源图没变、产物还在，直接复用，不重算。
   加 90 张图不该把 3000 张全部重新编码一遍 —— 那个长窗口正是撞车的机会。
2. **容错**：源图在运行中途消失（别人正在重命名），跳过并记下来，跑完统一报告，不再抛异常。

**效果**：水印从十几分钟 → **37 秒**（3009 复用 / 97 重算），
雷茵图集 → **8 秒**（3005 / 94）。撞车窗口从十几分钟缩到半分钟，
而且真撞上了也只是一行警告加一句「重跑一次即可收进来」。

> 没有加锁。甲方明确要求短反馈环、不要锁 —— 锁会阻塞另一个会话的提交流程。
> 增量把窗口缩到几乎不可能撞，容错让撞上了也不致命，这比锁便宜。

## 8. `bc7af2e4c6` 为什么没有提交消息

那个提交是本文件上一次更新（3.1 / 3.2 / 3.4 改成已完成、新增第 7 节），**内容是对的，**
**消息是空的**。

原因：上一条 `git commit` 撞上了 `.git/index.lock`（另一个会话正在提交），
我写了个循环等锁释放，用的是

```bash
until git commit -F /dev/null --allow-empty-message -q 2>/dev/null || ! ls .git/index.lock; do sleep 5; done
```

**这条命令本身就是一次提交。** 锁一释放它就成功了，把已经暂存的文件用空消息提交掉了。
我本意只是探测锁还在不在。

没有 `--amend` 修：那时它已经推送，而另一个会话正在同一分支上提交，
重写已推送的历史会打断它。`AGENTS.md` 里有同样形态的先例（`1bff2077`），
结论也是一样——消息留错，说明补在文档里。

**教训**：探测 `.git/index.lock` 就只 `ls` 它，不要拿一条真会改仓库的命令去试。
`AGENTS.md` 已经写了「不要把 heredoc 链在 `git add` 的 `&&` 后面」，
这是同一类错误的新形态：**把有副作用的命令当探针用。**
