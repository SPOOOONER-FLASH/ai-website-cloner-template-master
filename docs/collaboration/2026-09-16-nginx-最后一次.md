# nginx 还有什么要修：我全查了一遍，答案是「没有」

甲方 2026-09-16：「我已经提交四五次 nginx 了，每次都是重复一样的内容写到终端，
我想一次性修好搞完。」

这份文档回答两件事：**现在到底还缺什么**（查完了，答案在下面），
以及**为什么你会觉得在重复**，还有我做了什么让它不再重复。

---

## 一、先看结论

**服务器端现在没有已知的问题。** 不是「应该没问题」，是逐条打过请求的。

| 查了什么 | 结果 |
|---|---|
| 旧 `index.php` 重定向（9 个代表性形状） | **9 / 9 正确** |
| 旧产品 URL 随机抽样 | **40 / 40 正确**，落点全部是最终页，没有二次跳转 |
| `www` → 主域名 | ✅ 301 |
| `http` → `https` | ✅ 301 |
| 大写 `/Index.php` | ✅ 也能跳（Search Console 里有这种写法） |
| 找不到的页面 | ✅ 真的返回 404，不是假 200 |
| 找不到的图片 | ✅ 404 |
| HTML 缓存 | ✅ `max-age=300` + `stale-while-revalidate=60` |
| JS / CSS 带指纹的文件 | ✅ `max-age=31536000, immutable`（一年） |
| 图片 | ✅ `max-age=86400`（一天） |
| 压缩 | ✅ HTML / XML 走 brotli，JS / txt 走 gzip |
| HSTS | ✅ `max-age=31536000` |

> 这些是**打真实请求**得到的，不是看配置文件猜的。
> 想自己复现：`node scripts/verify-legacy-redirects.mjs`，最后一行应该是
> `9/9 legacy URLs redirect as intended.`

## 二、那两个 Bing 报的页面，本来就不用修

Bing 的 Site Scan 说这两个网址「head 里缺 description」：

```
https://cantonlock.com/index.php?m=home&c=Lists&a=index&tid=23&lang=cn
https://cantonlock.com/index.php?m=home&c=View&a=index&aid=397
```

**它们不是页面，是 301。** 没有 head，也就谈不上缺 description。

Bing 那一列写的是**它上次抓取时**的状态。2026-09-07 我们已经在同一个地方误判过一次 ——
差一点就让你去改生产环境的 nginx，修一个本来就在工作的东西。

**这类报告的读法：HTTP 状态那一列是历史，不是现状。要看现状就得发一次请求。**

## 三、但顺着查出来一个真的（已修，你已经上线了）

`aid=397` 当时跳到 `…/x2-panic-exit-device/`，而**那个网址自己又是一条 301**，
再跳到 `…-x2-panic-exit-device-trim/`。**跳两次。**

这样的有 **17 条** —— 15 条逃生器械，加 DS011 门吸和 LC04 锁体。
原因是 9 月 10 日那批产品改名之后，旧 `index.php` 的对照表没有跟着重新生成。

两跳能用，所以十一天没人发现。但第一跳攒下的排名会打折，而且它能成立只是因为
中间那条规则**碰巧还在** —— 哪天清理掉，旧网址就直接断了。

**这一条你 9 月 16 日已经跑过脚本上线了，现在 9/9 全对。**

## 四、为什么你会觉得在重复 —— 一半是真的，一半是我的问题

### 真的那一半：改不掉

这两个文件的内容**跟着产品目录变**。改一个产品的名字，旧网址的对照表就旧了。
只要还在改目录，就还得重装一次。**这部分消不掉**，任何做法都消不掉。

### 我的那一半：已经改了

以前我让你粘**两条**命令（先 `git pull`，再跑脚本）。两条命令 =
两次机会让第二条跑在旧代码上。**旧对照表能躺十一天，就是这么来的。**

**现在脚本自己会 pull，只要一条命令：**

```bash
bash /www/wwwroot/cantonlock.com/deploy/install-nginx-redirects.sh
```

### 另外两处也改了

| 改了什么 | 为什么 |
|---|---|
| 脚本现在会说「两个文件本来就一样，什么都没变」 | 「跑过了」和「本来就不用跑」是两回事，以前只会说前者 |
| 脚本的自检加了**旧 index.php 的三条**，而且比对**落点**不只看状态码 | 以前四条自检全是类目重定向 —— 那份最容易旧的文件，自检里一条都没有。它每次都报「All redirects live」，而那十一天里它是错的 |

⚠ **一个只验证不会出错的那份文件的自检，是装饰。**

## 五、以后什么时候还要跑

**只在我告诉你的时候。** 我这边现在有一道闸：`npm run test:export` 会重新生成这两份
配置并跟仓库里的比对，对不上就构建失败。所以「文件旧了」不会再悄悄发生。

> 我这边拦得住「仓库里的文件旧了」，拦不住「服务器上的文件旧了」——
> 那只有打线上请求才知道。所以我每次会自己跑一遍 `verify-legacy-redirects.mjs` 再告诉你。

### 跑完永远是同一件事

去 Cloudflare purge。**Cloudflare 会缓存 301**，不 purge 你在浏览器里测还是旧结果。

## 六、我没有让你做的一件事，以及为什么

查的时候发现四个「安全响应头」是空的：
`X-Content-Type-Options`、`X-Frame-Options`、`Referrer-Policy`、`Permissions-Policy`。

**我没有把它写进要你做的事，因为它对你要的东西没有帮助。**

| | |
|---|---|
| 对搜索排名 | 没有影响 |
| 对被 AI 引用 | 没有影响 |
| 对买家看到的东西 | 看不到 |
| 谁会看 | 极少数大企业采购的安全扫描 |
| 风险 | 不为零 —— 改一次生产环境的 nginx，就有一次弄坏的机会 |

真要加的时候，它可以并进同一个脚本，还是一条命令，不会变成第五次、第六次。
**现在不加。** 你要的是「一次性搞完」，而为一个买家看不见的东西再动一次服务器，
和这个目标是反的。
