## 一、动手之前必须知道的六条纪律

这些不是建议。前四条是甲方明确说过的，违反过一次就写进了 `AGENTS.md`。

### 1. Cloudflare purge —— agent 绝对不碰

甲方原话：

> purge 一会我来就行，写进纪律你们 agent 不要动，每次结尾你们确保 deploy 了 out/ 就行，
> 然后写一句记得 purge，其他的别浪费 token 了。

**不要**打开 Cloudflare 面板、不要找 API token、不要调 purge 端点、不要去查边缘缓存
为什么看起来是旧的、**不要暗示 purge 发生过**。构建 `out/`、提交、推送，然后回复末尾
写一句「记得 purge」。就这样。

### 2. 永远不生成想象出来的金属产品

甲方原话（是他老板当场否掉一批 AI 图之后说的）：

> 金属的孔位不对，螺丝不对，安装不上去，都不能用。
> AI 可以把现有的图片清晰化、白化，但是它不能想象产品。

**这是品类规则，不是质量标准，不是提示词写得更好就能过。** 孔位、螺距、方轴、backset、
中心距在开模前就定死了。生成出来的执手是一个装不上的零件，而买这个的人认得出型号 ——
他先认出型号，再看出它变形了，得出的结论不是「渲染不错」，而是这家供应商不懂自己的产品。

- ✅ 可以做：把**真实照片**修干净（去底、白场、曝光、透视、除尘、统一投影）；把多张
  真实照片按真实相对比例合成一张总览；修甲方自己拍的展会照片
- ❌ 不能做：生成不存在的产品；给真实产品加/减/改零件；拼一套工厂并不成套卖的组合；
  一张图里混不同表面处理；把重工业件和轻五金放同一框

**出图前自问**：买家能拿着这张图去车间下单吗？需要加任何前提，这张图就不发。

### 3. 「专业感」比「好看」重要

甲方老板原话：

> 真的是不需要花里胡哨，就让别人看起来专业，特别是五金方面，我们给别人专业的感觉，
> 他就会下单。因为金属太不容易自己手动了，工厂给人专业感觉，他们会睡得安稳。

买家买的是「这家不会出错」这个信念。所以：**写出来的尺寸胜过首屏动画，规格表胜过渐变。
一致性本身就是论据。不知道的就写破折号 ——** 一个编出来的数字被抓到一次，买家会把
所有数字都打折。

### 4. 白底图只放在 product finder

甲方：「首页和产品页都不要白底的图……白底请只放在 product finder。」

### 5. 共享工作树，永远不碰别人的未提交改动

Claude 和 Codex **同一个 checkout**，没有全局锁（甲方明确不要锁）。

- 陌生的未提交路径一律当作对方的：**不还原、不格式化、不移动、不暂存、不提交、不删除**
- Git Bash 的 `rm -rf` 绕过回收站，未跟踪路径也不在 git 历史里 —— 删了就是没了
  （2026-08-27 Claude 这样毁过 `tmp/codex-ar4-workbook-inspect`）
- 提交一律用 `git commit -F <消息文件> -- <明确路径>`。**不要**把 heredoc 接在
  `git add &&` 后面（2026-09-01 因此推出去一个只有警告行当标题的提交）
- 脏树**不是**阻塞信号。`out/` 一动就是约 5,000 个文件

### 6. 做完一条推一条

甲方：「不打断，你继续工作，做完一条推送一条，写进纪律。」

已授权的工作不要反复请示。分成能独立发布的阶段，每阶段验证、提交源码与产物、立即推送。
**每两三个完成的目标就 checkpoint 一次**：提交 + 写 agent-update + 让上下文缩小。
写在聊天里的东西下一次压缩就没了；写进跟踪文件才活得下来。

## 八、容易踩的坑（都踩过）

| 坑 | 症状 | 怎么办 |
|---|---|---|
| **搜索后台的 HTTP 状态是历史不是现状** | Bing 报 371 个旧 URL 返回 200 | 用 `curl` 实测。那 322 条是 7、8 月的**上次抓取**记录，重定向其实一直是对的 |
| **`node -e` 里的反引号和 `${}` 被 bash 吃掉** | 脚本行为莫名其妙 | 用 `node <<'EOF'` 带引号的 heredoc，或直接用 Edit/Write 工具 |
| **仓库里 LF 和 CRLF 文件混着** | 字符串锚点匹配不上 | 先 `JSON.stringify` 打印一行看看 |
| **Tailwind v4 会扫 `out/`** | 截断的 RSC 类名导致非法 CSS，dev 报 500 | `globals.css` 顶部已有 `@source not "../../out"` |
| **`delete record.heroImage`** | 7 条记录少了这个 key，构建挂掉 | 目录既定形状是 `heroImage: {ratio, label}` 无 `src`（80 条这样用）。**不要**把类型改成可选，那会连锁出 46 个 TS 错误 |
| **并发写 `content/products` 时导入脚本会崩** | 读到瞬时的空 JSON | 逐目录跑，别一次传 30 个目录。**并且不要用 `grep` 过滤脚本输出**，会把报错一起滤掉（因此曾静默漏掉 18 个型号） |
| **`.git/index.lock` 残留** | git 全部报错 | 先确认零个 git 进程、文件 0 字节、且有年纪，再删，删完核对 HEAD 没变 |
| **predeploy 新鲜度失败** | 「out/ 比源文件旧」 | 构建期间不要改源码；不要并发跑两个构建；对方在写文件时就只提交源码，`out/` 留给持棒的人 |

## 九、发布流程

```bash
npm run deploy:prep          # build + 保留旧资产 + 导出审计 + 新鲜度检查
git add -- <明确路径> out/   # 绝不用无审阅的批量暂存
git commit -F <消息文件> -- <明确路径>
git push                     # 12,000 个以上文件的推送可能要跑十几分钟，正常
```

推完在回复末尾写一句：**记得 purge**。不要多写。

`out/` 是否已经脏了决定接力棒在谁手里 —— 脏了就是别人在构建，你只提交源码，
在自己的 agent-update 里说一句构建归他们。
