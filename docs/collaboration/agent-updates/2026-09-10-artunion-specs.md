## 怎么匹配的：只认品番，不认标题和图片

`POST /products/search_id.php` 带 `id=<型号>` 会返回结果页路径，页里列出该型号的全部
变体（G1106 → G1106-01-011 / -015 / -024），每个变体有 `detail.php` 详情页。
按标题或缩略图匹配是猜，品番是厂家自己的键，要么精确命中要么算没命中。

**按长度取一个变体，不是按表面处理。** 品番结构是 `<型号>-<材质>-<颜色>[-L<长度>]`，
我们要的重量/ピッチ/孔径随**长度**变，不随表面处理变。按表面处理抓，G2750 要发 15 次
请求还会漏掉长度 —— G2690 有 20 个变体，我们实际在卖的 1660–2160 可调那款不在前四个里，
一开始被判成「冲突」，其实只是没抓到那一行。

## 自我校验：中心距双向印证

抓到的 ピッチ 必须等于我们自己从图纸上读的中心距。两个独立来源对上同一个尺寸，
是这里能拿到的最强证据，而且它同时**锁定了是哪个长度**。

| 结果 | 数量 |
|---|---|
| 中心距双向印证 | 28 |
| UNION 只发布一个长度，无歧义 | 7 |
| 长度多、图纸无中心距，无法定位 → 跳过 | 1（T2110） |
| UNION 未收录 | 6（PRE 系列 5 个 + T2973A） |

G3078 是一个型号两个长度：L600 的 ピッチ 是 582，L800 是 782，我们图纸写 782。
只比对第一个变体会把它判成冲突，然后丢掉一条正确的匹配 —— 型号是对的，长度不对。

## 明确不抓的四项

| 字段 | 为什么 |
|---|---|
| 価格 | 甲方指示不抄价格；UNION 的日元定价与本厂报价无关 |
| 施工実績 | 那是 UNION 的项目（帝国ホテル京都、丽思卡尔顿日光…），抄过来是直接说谎 |
| 機能 | 「アートセーフ対応」是 UNION 的品牌项目，不是金属的属性 |
| カタログ | UNION 自己样本册的页码 |

这四项仍写进缓存供人查阅，合并脚本拒绝把它们写到产品上。

## 两个没图纸的型号：撤回，不发布

`src/data/product-sites.test.ts` 有一条规矩：没有图纸的型号，规格表必须是空的。
它写的理由是「不许从同款抄尺寸」，而我们手上的比那个强 —— 是 UNION 自己按同一品番
发布的记录。所以一度很想认为这条规矩不适用。

**它适用。** 因为这次合并里每一行的安全论证都是「两个独立来源对上了中心距」。
对一个我们没有图纸的型号，没有第二来源、没有可对照的东西，也没办法发现那条记录
其实属于另一个长度或另一个版本。受影响的只有 G1216 和 T2973，两条重量不值得拿
「这个站上每个数字都可复核」这条不变量去换。客户补了图纸，它们自己就会脱离这个名单。

## 顺带印证了 G/T 前缀的含义

之前是靠比对 11 张图纸 + 14 块产品铭牌推断 G/T 是安装方式。这次 UNION 的 施工 字段
独立印证了：

- **G**：取付穴 φ12mm，フラッシュドア取付時 φ8mm → 默认玻璃门
- **T**：取付穴 φ10mm，ガラスドア取付時 φ16mm → 默认平板/木门

## 规格值里不许有句子

第一版把孔径写成一个值：`φ12mm, on flush doors: φ8mm`。中文镜像把它变成
`φ10mm, on 玻璃门: φ12mm` —— 半中半英，正是镜像专门要防的那一种输出。
问题不在翻译表，在于**把一个句子放进了本该放尺寸的位置**。门型是标签，所以门型进标签：

```
安装孔径            φ12mm
安装孔径（平板门）   φ8mm
```

值恢复成纯尺寸，镜像根本不用碰它。
