## 分类：G 和 T 不是两个前缀，是两种安装

17 个型号里，`G*` 和 `T*` 成对出现（G1130/T1130、G1216/T1216、G2110/T2110）。
把 11 张尺寸图和 14 张产品图排在一起看，两组的画法**系统性不同**：

| | 产品图 | 尺寸图 | 结论 |
|---|---|---|---|
| `G*` | 磨砂玻璃门扇 | **不画门**，只标杆长与立柱直径 | 玻璃门拉手，穿孔固定，杆长随玻璃厚度配 |
| `T*` | 实体门扇（深色门＋浅色框） | **画了门扇断面**，并标出墙距离 33 / 35 / 54mm | 门拉手，单面安装 |

所以：

- `G*` → `glass-door-accessories/glass-door-handles`（玻璃门拉手，现有 16 个型号）
- `T*` → `stainless-steel-handles`（该类目现有 44 个型号，实际就是大拉手类目）
- `UL* / MUL*` → `lever-handles`（执手）

这是从图上看出来的，不是按前缀猜的 —— 我先按「G=玻璃」猜过一轮，
被 G2750 的实景照推翻了（它同时出现在玻璃隔断和木门上），
才回去逐张比对图纸画法。**安装方式才是那条稳定的线。**

## 规格：只写图纸上印着的数字

11 个型号有 `D900SZ` / `D921SZ` 尺寸图，逐条读进 specs：中心距（P=）、总长、
出墙距离、管径、圆盖尺寸、执手长度。全部 11 张图纸都是「P= 是孔距，下面那个大数是总长」
这个关系，所以读法本身是自洽的，不是逐张猜。

**4 个型号没有图纸**（G1216、G2110、T2973、MUL1022），规格表是**空的**。
没有套用同族型号的尺寸 —— 同一款式的 G 和 T 长度不同、固定方式不同，
「差不多」在这里就是孔位错，买家损失一整批货。
`product-sites.test.ts` 里有一条测试专门锁这个方向：**没图纸却写了尺寸行会挂**。

## 「同款式搭配」：存一次，两个方向都推出来

客户那句「有门把手的表示此款式搭配有同风格的门把手」，在数据里落成
`Product.styleFamily`（一个字符串，如 `"1130"`）。页面上：

- 拉手页显示「**本款配套同风格门把手 UL1022、MUL1022，可成套下单。**」
- 执手页显示「本款执手属于同一设计款式，可与下列拉手成套使用。」

**没有存成两份 partner 列表**，因为那种写法会漂：改了拉手页忘了改执手页，
结果是拉手推荐了一个执手，而那个执手的页面从来没提过这个拉手。
从 `styleFamily` 推导则不可能不对称，测试也断言了这一点。

这个区块**排在「同类型号」上面**。两者回答的问题不一样：同类型号是「我还能买什么替代」，
同款式搭配是「这扇门后面那几扇门要配什么才一致」。后者才是把订单做大的那个，
而且是买家自己翻目录翻不出来的。

### 测试抓到我自己写错的一处

第一版 `union-handles.json` 给 G1289、G1293、G2750 都写了 styleFamily，
但它们各自在已上架的型号里**没有同伴**（前两个本来就是单型号包，G2750 的两个同伴被我
held back 了）。「同款式搭配」会渲染成一个空区块，字段本身是句假话。

改法不是手工删那三行，而是让脚本自己算：**一个款式至少要有两个已上架成员才成立**，
不满足就不写这个字段。客户补齐 TSG2750 / USG1 的产品图那天，它会自己恢复。

## 又修的一处：这个脚本在 Windows 上会中途崩，而且崩得看不出来

重跑雷茵图集时它死在第 300 张左右：

```
Error: ...\public\images\products-rayen\47bsik-lock-cylinder.webp: unable to open for write
system error: Invalid argument
```

随机一个文件、随机一次，最像是杀软的实时扫描还占着它刚写完的句柄。

**问题不在崩，在崩的方式。** 上一轮的 manifest 还留在磁盘上，看起来一切正常，
而后面 2000 多张图保持着旧内容 —— 我就是这么被骗了一轮：以为豁免没生效，
其实是脚本根本没跑到那些文件。后台任务的退出码还被包装成了 0，
所以连「失败了」这个信号都没有。

改成：写失败重试一次，再失败就记下来继续跑完，最后把失败清单打出来并
`process.exitCode = 1`。跑完是完整的，失败是可见的，退出码不骗人。

## 我在这次提交里干砸的一件事，记下来

暂存时用了 `git add -A -- content`。范围太宽 —— 另一个会话当时正在写产品视频，
五个刚新建的 JSON 被我在**写到一半**的瞬间暂存进去，提交里是截断的、解析不了的内容
（bh55/bh56/bh57/bh58、dv04）。任何人 checkout 那个提交都会构建失败。

发现是因为提交完 `git status` 里还剩 39 个改动，去查「为什么还没干净」。
**如果没去查，这个提交会带着五个坏 JSON 推上去。**

修的时候差点又砸第二次：想把它们还原成上一版，跑了
`git show HEAD~1:file > file`，但这五个文件在 `HEAD~1` 里根本不存在（是新建的），
git 报错退出，而 shell 的重定向**已经先把文件清成 0 字节了**。
幸好动手前先 `cp` 了一份备份，五个文件原样恢复。
**先备份再动别人的文件，这一步不能省。**

AGENTS.md 里已经写了「按明确路径暂存，不要在脏树里用未经审阅的批量暂存」。
以前担心的形态是「覆盖别人已有的改动」；这次是新形态：**给别人正在写、还没写完的
文件按了快门**。目录级的 `git add -A -- <dir>` 在共享工作树里等同于批量暂存。
