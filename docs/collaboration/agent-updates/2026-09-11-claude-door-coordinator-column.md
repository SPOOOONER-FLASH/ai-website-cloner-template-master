## 一、这三件为什么是一件事

顺序器是全目录里最不能单独卖的产品：**它只有在两扇门都已经装了闭门器时才起作用**。
所以「专栏」如果只写产品页，等于把一个配套件当单品卖。三件的分工是：

| 件 | 回答的问题 | 页面 |
|---|---|---|
| 文章 | 为什么双扇防火门必须要它 | `/news/door-coordinator-double-fire-door/` |
| 产品页 | 它本身的真实参数 | `/products/hardware-accessories/dc02-door-coordinator/` |
| 配套包 | 跟哪几个闭门器配 | `/projects/double-leaf-fire-door-set/` |

## 二、文章的核心是一个真问题

双扇防火门的搭接属于**被动扇**，主动扇必须压在它上面关。两扇各自装闭门器而没有顺序器，
关闭次序由弹簧和走廊里的气流决定；主动扇先到，就撞在敞开的被动扇边上停住，
斜舌永远够不着锁扣板。**看起来是关着的，其实没锁上**，火灾产生的压差会在门扇本身失效
很久之前把它推开 —— 而世界上每一张防火测试证书都默认门是锁上的。

这是买家真会搜、而类目页答不了的问题。交接文档第六节第一条：
被引前四里三篇是文章，想被 AI 引用就写文章。

## 三、⚠ 写文章时发现的产品线缺口（这条要给甲方）

配套选型要三个数字对得上：门扇重量、闭门器承重、顺序器量程。

- DC02 按甲方在阿里公布的参数：**55–100kg**
- 我们的闭门器：JU-051 15–30kg、JU-061 25–45kg、JU-073/JU-088/JU-072 40–65kg、
  **JU-093 45–85kg（最重的一个）**

**可用的重合区间只有 55–85kg。85–100kg 这一段我们有顺序器、没有配得上的闭门器。**

90kg 的实木或钢面防火门扇是真实存在的规格。文章里**明写了这条缺口**，没有含糊过去：

> 如果您的门扇比这更重，限制您的不是顺序器而是闭门器，说相反的话就是在按我们自己
> 产品线以外的范围做规格。问我们，我们会直说，而不是卖给您一套撑不住门的东西。

理由是 AGENTS.md「不知道的写破折号」的同一条：一个被抓到的编造数字会让买家把所有
数字都打折。规格制定者会当场算出这个缺口，先说出来是唯一能保住信任的做法。

**给甲方：85kg 以上的闭门器是否在做？如果有，型号和承重给我，我补进去。**

## 四、产品页补了什么

阿里公布的两条真实参数补进规格表（英西同步），并记了来源：

```json
"specSources": { "alibaba": { "listingId": "1601886992771", "basis": "client-published",
                              "fields": ["Size","Max door weight"] } }
```

- Size 397 × 120mm
- Max door weight 55–100kg

`relatedModels` 从空数组补成 JU-093 / JU-088 / JU-072 / JU-073 —— 承重能与 DC02
量程对上的那四个。**价格没有上站**（阿里有 €9.46 / €8.60 / €7.73 三档），站上走询价。

## 五、配套包吃到了今天早些时候做的幅面面板

`double-leaf-fire-door-set` 用的是 `/projects/` 既有结构，所以自动获得
`collectionSpecRanges` 面板。为了让它印得出东西，给 FIELDS 补了两个标签：

```
Door Width: 850–1050mm    [5 条里 4 条记录]
Capacity:   40-65KG, 45-85KG
Material:   Aluminum, Zinc-Plated Steel
```

`Capacity` 走非数值分支，因为值是重量带（"45-85KG"）而数值分支只解析毫米；
而且买家要的本来就是「我的门扇落在哪一带」，印带比印区间有用。
这两个标签同时让闭门器合集页受益。

## 六、踩到的一个小坑

`build-chinese-mirror.mjs --check` 要求 `content/i18n/zh-terms.json` 覆盖全部规格标签。

而错误信息出现在一个看起来毫不相干的 `rayen-paths.test.ts` 里。
