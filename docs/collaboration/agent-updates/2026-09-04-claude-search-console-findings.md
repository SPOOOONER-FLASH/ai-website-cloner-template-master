# 2026-09-04 · Claude · Search Console 与装箱表读出来的四件事

甲方发来 Bing 关键词截图、一张装箱表照片，以及两份 Search Console 导出。

## 一、`abs-015` 是全站最大的关键词信号，而那一页的介绍只有四个词

Bing 关键词工具：**`abs-015` — 169 次展示**。

015 这一页是上线的，有 7 张图库图和 1 段视频。它的整段介绍是：

> ABS panic exit device.

二十二个字符。**全站最大的单个关键词信号，落在一个描述只有四个词的页面上。**

已改写，只用这张记录自己的规格行（`Used in combination with push bar and lock`、
`ABS`、`BN`、`Up to 80mm`、`Includes 3 brass keys`），没有增加任何新说法。

### 顺带修了 meta description 生成器的排序

那句改写完 147 字符，一开始没进 snippet —— 因为它是**追加在属性子句后面**的，
在抢剩余字符，而 `fitToBudget` 是从末尾丢起的。

排序改成：开头 → **人工核对过的那句** → 属性子句 → 样板。
位置就是优先级，而「External handle for panic bar systems」比
「Available in BN finish.」更值得那些字符：前者告诉搜索者这是什么，
后者告诉他一件到了页面上自己会看到的事。

样板占比 **47% → 31%**，以样板结尾的从 410 降到 344，截断 0 条，重复 0 条。

## 二、15 个产品在我们站上叫「逃生锁」，在贵司自己的 stahlock 上叫「外装执手」

015 的 stahlock 页面标题是 **`STAHLOCK MODEL: 015 - Trim Handle`**。

写了 `scripts/audit-name-drift.mjs` 全量对比，**18 个型号两边叫法不一致**，
其中 15 个是「Panic Exit Device ↔ Trim Handle」。

**这不是同义词。** 逃生推杆是装在门内侧、人一撞就开的那根杆；
外装执手是配合它使用的门外侧把手。搜逃生锁的买家点进来看到的是一个把手。

四处独立证据都指向「外装执手」，而且全部是甲方自己的材料：

| # | 证据 |
|---|---|
| 1 | stahlock 页面标题（甲方 9/4 确认过是人工核对的） |
| 2 | 我们自己 015 的规格行：*Used in combination with push bar and lock* |
| 3 | 027 从 stahlock 搬来的描述：*External handle for panic bar systems* |
| 4 | 016 从 stahlock 搬来的描述：*Outside Lever Trim with Key … designed for panic exit devices* |

**我没有改名。** 改名会移动 URL，而 015 这个 URL 正在有排名 —— 移动一个正在排名的
URL 需要配 301、页面历史会重置，而依据只是另一个站的页面标题。
清单在 `Desktop\hyde\产品命名不一致清单.html`，三选一勾一下就行。

比较对的是**名词**而不是字符串：`607 SSET Tubular Lock` 和
`STAHLOCK MODEL: 607 SSET - Tubular Lock` 是同一个名字的两种排版，
逐字比会把 305 个全报成不一致。

## 三、装箱表：3 行能安全上线，但它证明了整件事值得做

### 先说量出来的结果

| 页面 | 可引用数字 |
|---|---|
| 全部 457 个英文产品页平均 | **4.7** |
| 5688（新增装箱数据） | **15** |
| 5689（新增装箱数据） | **19** |
| 027（新增装箱数据） | **10** |

**五行装箱数据把一个产品页的可引用数字变成 2–4 倍。**
GEO 报告里「补装箱数据」一直是第一条建议，现在它有了量出来的倍数：
补齐其余 432 个，产品详情页这一档会从 4.7 走到 10–15，
也就是从 55 分走到对比页那一档（68）。

### 为什么 26 行只用了 3 行

**表面处理会改变箱规，而且是这张表自己证明的。** 第 6、7 行是同一把锁的两个表面处理 ——
808 SS ET 和 808 PB ET —— 箱规分别是 57.2×19.1×47.5 和 42×35×31.8。
那不是四舍五入的差别。

所以一行装箱数据**不能摊到一个型号的各个表面处理上** ——
而这恰恰是能让 `D101、D102` 覆盖 D101 的五个表面处理、
让 `70710-AB` 覆盖 70710 PB 的那个捷径。这张表把它否掉了。

另外：607 SS ET 出现两次（吸塑 24 只 / 纸盒 30 只），026 出现两次（24 只 / 16 只），
808 SSBK 出现两次且表格自身列错位（体积栏是 `#REF!`）。照片里看不出哪个是现行的。
装箱数字是要抄进形式发票和提单的，写错就是一个装不进客户订的柜的货。

整张表按原样转录进 `content/packing-data.json`，每一行都标了状态和不采用的理由 ——
照片会丢，转录不会。体积栏也全部按箱规重算过：18 行里 14 行分毫不差，
另外 4 行记下差异而不是悄悄改掉。

## 四、旧西语首页把西语买家送到了英文页

Search Console：`https://www.cantonlock.com/index.php?lang=es` ——
**31 次展示，平均排名 4.97**，全站排名最好的几个 URL 之一。

它 301 到**英文的** `/products/`。西语买家从西语结果点进来，落在英文栏目页。

另外光秃秃的 `index.php`（旧首页）也被送到 `/products/` ——
那是在回答没人问的问题，还丢掉了首页自己积累的排名。

三个 map 变量已经生成进 `deploy/nginx/legacy-redirects.conf`：

- `$legacy_lang_prefix` —— 把语言带到 aid/tid 解析出的目标上，所以旧的西语类目 URL
  会落到西语类目页。map 输出的每一个目标都有西语镜像，加前缀是安全的。
- `$legacy_lang_home` / `$legacy_fallback_path` —— 区分「有参数但没解析出来」
  （→ `/products/`）和「什么都没有」（→ 首页）。

⚠ **需要甲方手工改一个 location 块**，因为它在宝塔管理的主 vhost 文件里，
安装脚本按设计不碰那个文件。逐步操作已写进 `CLIENT-RUNBOOK.md` 第 1b 节 ——
含备份、逐字对照、保存失败怎么回滚、以及五条验证命令的预期输出。

## 一个我自己制造又修掉的缺陷

往运维手册里插新章节时用了 `String.replace`，而替换文本里含 `$'` ——
JavaScript 把它当成「匹配之后的全部内容」，于是整份手册被复制了一遍。
改成 split/join，并把原因写在插入脚本的注释里：替换文本是整段散文时，
`$&`、`` $` ``、`$'`、`$1` 都是雷，而失败长得像文件重复而不是像报错。
